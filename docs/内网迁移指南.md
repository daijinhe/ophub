# 内网迁移与发版指南

平台最终运行在**与互联网隔离的内网**，而开发在本地有网环境进行。本文说明两件事：

- **首次迁移**：怎么把平台和数据完整搬进内网，一次跑通。
- **日常发版**：本地开发完 → 推内网 Harbor → 内网自动拉取重启。

---

## 1. 为什么不能在「内网直接构建」

内网的网络限制决定了构建必须在本地完成：

| 依赖 | 地址 | 内网可达性 |
|---|---|---|
| Go 基础镜像 / 依赖代理 | `swr.cn-north-4.myhuaweicloud.com`、`goproxy.cn` | ❌ |
| Node 基础镜像 / npm 源 | `swr.cn-north-4.myhuaweicloud.com`、`registry.npmmirror.com` | ❌ |
| PostgreSQL / Redis 基础镜像 | `swr.cn-north-4.myhuaweicloud.com` | ❌ |

所以约定：**本地构建镜像 → push 到内网 Harbor → 内网只 pull + 起容器**。
`docker-compose.yml` 里的 4 个镜像地址已全部变量化，内网通过 `.env` 指向 Harbor 即可，
**内网不需要源码目录**。

```
本地（有网）                                    内网
├── 源码 + git                                  ├── Harbor  harbor.internal.example/your-project
├── docker build ──── push ────────────────────>│
└── migrate_export.sh ─── 迁移包 ──────────────>├── 部署机 /opt/ophub
                                                │     docker compose pull && up -d
                                                └── 平台容器 ──SSH──> Ansible 控制节点 ──> 目标机
```

## 2. 前置准备

### 2.1 本地开发机

1. **Docker Desktop 信任 HTTP 仓库**（内网 Harbor 是 HTTP，非 HTTPS）。
   编辑 `%USERPROFILE%\.docker\daemon.json`，加入：

   ```json
   {
     "insecure-registries": ["harbor.internal.example"]
   }
   ```

   保存后**重启 Docker Desktop**（`docker desktop restart`），用
   `docker info | grep -A4 "Insecure Registries"` 确认已列出该地址。

   > 不配这一步，push 会报
   > `http: server gave HTTP response to HTTPS client`。

2. **填 Harbor 配置**：`cp .env.harbor.example .env.harbor`，填好地址与账号。
   密码建议留空，首次 push 时交互输入，docker 会缓存到系统凭据管理器。

### 2.2 内网服务器

1. 装好 Docker + Docker Compose v2（`docker compose version` 能输出版本）。
2. **同样配 `insecure-registries`**（`/etc/docker/daemon.json`），然后
   `systemctl restart docker`。两边都要配，只配一边会在另一半失败。
3. 能 `ping` / `curl` 通 Harbor：`curl -i http://harbor.internal.example/v2/`
   返回 **401** 即为正常（服务在，需认证）。
4. 到 Ansible 控制节点的 SSH 必须通（平台所有远程采集都走这条路）。

## 3. 首次迁移（一次性）

### 阶段一 · 镜像入库（本地）

```bash
bash scripts/harbor_release.sh --with-base
```

`--with-base` 会额外把 `postgres:16`、`redis:7.4.10` 两个基础镜像也推进 Harbor——
**首次迁移必须加**，否则内网起不来数据库。

成功后在 Harbor 的 `your-project` 项目下应能看到 4 个仓库。

### 阶段二 · 导出数据（本地）

```bash
bash scripts/migrate_export.sh
```

产出 `dist/ophub-migrate-<版本>-<时间>.tar.gz`，内含：

| 内容 | 说明 |
|---|---|
| `db/ophub.sql.gz` | 数据库全量导出（含表结构） |
| `db/ROWCOUNTS.txt` | **逐表行数快照**，内网导入后自动比对 |
| `env/.env` | 环境变量，**含 JWT_SECRET / PWD_ENC_KEY** |
| `compose/` | docker-compose.yml 与 .env.example |
| `scripts/` | 内网侧脚本（导入、更新） |

> ⚠️ 这个包等同于密钥文件，请走安全通道传递，不要用邮件或聊天工具。

### 阶段三 · 传到内网并导入

```bash
# 内网服务器上
mkdir -p /opt/ophub
tar -xzf ophub-migrate-*.tar.gz -C /opt/ophub
cd /opt/ophub
bash scripts/migrate_import.sh
```

脚本会自动按顺序完成：

```
环境检查 → 生成 .env（镜像指向 Harbor）→ docker login → 拉取镜像
→ 启动 PostgreSQL/Redis → 恢复数据库 → 逐表比对行数
→ 启动 backend/frontend → 健康检查
```

全部通过时结尾会打印访问地址。若 Harbor 地址与导出时不同：

```bash
bash scripts/migrate_import.sh --harbor harbor.internal.example --project your-project
```

若 Harbor 暂时不可用，可用离线通道（迁移包需带 `--with-images` 导出）：

```bash
bash scripts/migrate_import.sh --load-images
```

### 阶段四 · 迁移后必做（容易漏）

| # | 事项 | 怎么改 |
|---|---|---|
| 1 | **Ansible 控制节点地址** | 界面「**资源配置 → 主机清单**」里改 host/端口/账号；内网平台访问不到 `platform.internal.example` / `203.0.113.181`。改完点该节点的「测试」，出现 `PING-OK` 才算通 |
| 2 | **资产 IP / 网络区域** | 内网资源池若与现网不同，需重新校准或改登记值，否则采集全部失败 |
| 3 | **管理员密码** | 默认 `admin/admin123`，登录后立即改 |
| 4 | **`ENV=prod`** | `.env` 里把 `ENV=dev` 改成 `prod`（会强制校验密钥强度，我们的密钥已达标） |
| 5 | **`.env` 保管** | 迁移包用完后从内网删除，或移入受控目录 |

### 阶段五 · 验收清单

导入脚本会自动跑完前 2 项；后 3 项需要在界面上点一下。**第 4 项是全套里最关键的验证**——
它同时证明「数据搬全了」和「`PWD_ENC_KEY` 搬对了」。

- [ ] `docker compose ps` 四个容器都是 `Up`，postgres/redis/frontend 显示 `(healthy)`
- [ ] 结尾打印 `全部 N 张表行数一致 ✓`（脚本已自动比对 `db/ROWCOUNTS.txt`）
- [ ] 浏览器能打开 `http://<内网IP>:10001`，`admin` 能登录
- [ ] **「资源配置 → 主机清单」点控制节点的「测试」，返回 `PING-OK` 且 `status: online`**
      —— 平台能拿库里的密文解出 SSH 密码并连上控制节点，
      说明加密密钥与凭据数据都是完好的
- [ ] 主机清单能列出各分组的 hosts（与现网一致）
- [ ] 资产列表数量与现网一致；随便点开一个资产，详情能正常打开
- [ ] 定时任务 / 中间件捕捉能跑通一次（这条会把 Ansible 通道全链路走一遍）

## 4. 日常发版（本地 → 内网）

### 本地：构建 + 发版 + 推 Harbor

```bash
bash scripts/harbor_release.sh --git "feat: 新增 xxx 功能"
```

这一条命令做了四件事：`release.sh` 升版本号并提交打 tag 推 git → 构建前后端镜像
→ retag 成 Harbor 地址 → push（同时推 `:<版本>` 和 `:latest`）。

也可以分两步走，便于控制：

```bash
bash scripts/release.sh "feat: xxx"      # 只走 git
bash scripts/harbor_release.sh           # 只推镜像
```

### 内网：拉取新版本

```bash
bash scripts/harbor_update.sh --tag v1.7.6   # 切到指定版本（推荐，可控）
bash scripts/harbor_update.sh                # 按 .env 当前 tag 重拉，有变化才重建
bash scripts/harbor_update.sh --check        # 只查看当前状态
bash scripts/harbor_update.sh --rollback     # 回退到上一个版本
```

### 内网：全自动（可选）

```bash
# 每 10 分钟检查一次；镜像无变化时脚本会直接退出，不会重启容器
*/10 * * * * cd /opt/ophub && bash scripts/harbor_update.sh --latest >> /var/log/ophub-update.log 2>&1
```

> 用 `--latest` 图省事的代价是**无法从版本号判断线上跑的是哪一版**。
> 若需要可追溯，改用固定版本号 + 人工改 `.env`。部署历史会记在 `.deploy_history`。

## 5. 回滚

### 应用回滚（快，秒级）

```bash
bash scripts/harbor_update.sh --rollback
```

前提：Harbor 上还留着旧版本镜像（`harbor_release.sh` 按版本号推送，天然保留）。

### 数据回滚

数据走的是 Docker 命名卷 `ophub_pgdata`。定期备份：

```bash
docker exec ophub-postgres pg_dump -U ophub -d ophub --no-owner \
  | gzip -9 > backup-$(date +%Y%m%d).sql.gz
```

恢复：`gunzip -c backup-xxxx.sql.gz | docker exec -i ophub-postgres psql -U ophub -d ophub`

## 6. 坑位清单（每一条都实际踩过）

### 6.1 `PWD_ENC_KEY` 变了 = 所有凭据报废

数据库里的资产密码是 AES-GCM 加密存储的（`enc:v1:` 前缀），密钥来自 `PWD_ENC_KEY`。
**换了这把钥匙，历史密文一条都解不开**。迁移时 `.env` 里的
`JWT_SECRET` 和 `PWD_ENC_KEY` 必须原样搬过去，绝不能「在内网重新生成一份」。

### 6.2 compose 项目名不固定 → 数据「凭空消失」

compose 的卷名 = `<项目名>_<卷名>`，项目名默认取**当前目录名**。
把部署目录从 `ophub-migrate` 改名成 `ophub`，compose 就会去找 `ophub_pgdata`
而不是 `ophub-migrate_pgdata` —— 容器起来了，但数据是空的。

本项目的 `docker-compose.yml` 已写死顶层 `name: ophub`，目录怎么改都不受影响。
**不要删这一行**。

### 6.3 两边都要配 `insecure-registries`

Harbor 是 HTTP。只给内网服务器配、忘了本地开发机，push 就失败；
只给本地配、忘了内网，pull 就失败。报错关键字都是
`server gave HTTP response to HTTPS client`。

### 6.4 架构必须一致

镜像默认按本机架构构建（本项目为 `linux/amd64`）。
内网服务器若是 ARM，需设 `TARGET_PLATFORM=linux/arm64` 重新构建推送，否则报
`no matching manifest for linux/arm64`。

### 6.5 WebSocket 终端连不上

平台鉴权采用的是「同源放行」策略（见 v1.7.2 修复）。内网用 IP 或域名访问都能正常工作，
`ALLOW_WS_ORIGINS` **留空即可**。

只有当平台前面还挂了一层反向代理、导致前后端不同源时，才需要显式列出，例如：

```
ALLOW_WS_ORIGINS=http://ophub.corp.com
```

另外若内网也用 nginx 反代，务必用 `proxy_set_header Host $http_host`——
用 `$host` 会丢掉端口，同源判定会失败（这是 v1.7.2 踩过的坑）。

### 6.6 首次连 SSH 会"卡"一下

平台首次连接一台新资产时会把主机公钥 PIN 到 `known_hosts.json`（防 MITM），
之后严格比对。该文件现在挂在命名卷 `ophub_backend-data` 上，容器重建不会丢。

如果内网是「同镜像批量迁移」场景、希望临时放宽，可设 `ALLOW_TEMP_TRUST=true`
（PIN 只存内存），但**正式环境建议保持 false**。

### 6.7 脚本管理的挂载目录

`docker-compose.yml` 会把宿主机的 `/data/jenkins_home/scripts/Java_Start_Stop_SH`
挂进容器（脚本管理的「平台本机」模式）。内网如果没有这个目录：

```bash
sudo mkdir -p /data/jenkins_home/scripts/Java_Start_Stop_SH
```

路径可在 `.env` 里用 `SCRIPT_HOST_ROOT` 覆盖。
若不挂这个目录，页面上会列不出任何脚本（后端读到的是容器内的空目录）。

### 6.8 目标机已有同名容器会冲突

`docker-compose.yml` 里的 `container_name` 是固定的（`ophub-postgres`、`ophub-backend` …），
好处是运维命令好写，代价是**同机不能并存两套**。若目标机上已跑过一套（例如迁移前试部署过），
`up` 会报：

```
Conflict. The container name "/ophub-postgres" is already in use
```

先清掉再部署：

```bash
docker compose down --remove-orphans     # ⚠️ 千万不要加 -v，加了会连数据卷一起删
```

### 6.9 `migrate_import.sh` 会把数据写进哪套库？

`container_name` 是固定的（`ophub-postgres`），所以**同一台机器上只有一套能叫这个名字**。
但如果机器上跑着**另一套**平台（compose 项目名不同、容器名刚好也叫 `ophub-postgres`），
或者你在错误的目录里执行了导入脚本，恢复数据就会**覆盖别人的库**——这是不可逆的。

脚本为此加了两道保护：

1. 读 PG 容器的 `com.docker.compose.project` label，与当前目录 `docker-compose.yml` 的
   顶层 `name:` 交叉比对；不一致时**要求手工输入 `yes`**才继续：
   ```
   [warn] 目标数据库容器「ophub-postgres」属于 compose 项目「ophub」，
          而当前部署项目是「ophub-migrate-test」
   [warn] 继续会把数据写进「ophub」那一套环境，而不是当前目录这一套。
     确认仍要写入 ophub 吗？输入 yes 继续：
   ```
   看到这个提示**先停下来确认**：你是想在当前目录这套环境里导入，还是想写另一套？
2. 目标库非空时会提示「继续会 DROP 并重建」，同样要求确认（或用 `--force --yes` 跳过）。

同机多环境调试时，用 `PG_CONTAINER=<容器名>` 显式指定要操作的库，避免打到默认那个：

```bash
PG_CONTAINER=tophub-postgres bash scripts/migrate_import.sh --yes
```

### 6.10 迁移包只搬数据库，不搬卷

迁移包里的 `db/ophub.sql.gz` 是整个 PostgreSQL 库，**业务数据全在这里**。
另外两个卷不在包内：

| 卷 | 内容 | 不带过去的影响 |
|---|---|---|
| `ophub_backend-data` | `known_hosts.json`（SSH 主机公钥 PIN 库） | 无影响。内网首次连每台资产会自动重新 PIN |
| `ophub_backend-uploads` | 页面上传的 Excel 等临时文件 | 无影响，都是可重新上传的中间产物 |

`ophub_ansible-data`（`/etc/ansible`）本来就是空的——主机清单文件存在**控制节点**上，不在平台侧。

`known_hosts.json` 曾长期躺在容器文件系统里（重建即丢）。v1.7.5 起它挂到了命名卷上，
本地已有的 PIN 记录已通过 `docker cp` + 卷灌入的方式保留下来（5 条，sha256 校验一致），
所以本地环境下次重建容器**不会**要求重新 PIN。

## 7. 文件速查

| 文件 | 作用 | 在哪边用 |
|---|---|---|
| `scripts/harbor_release.sh` | 构建 + 推 Harbor | 本地 |
| `scripts/migrate_export.sh` | 导出数据 + 配置成迁移包 | 本地（首次） |
| `scripts/migrate_import.sh` | 导入数据 + 启动全栈 | 内网（首次） |
| `scripts/harbor_update.sh` | 拉取新镜像并重启 | 内网（每次发版） |
| `scripts/release.sh` | 升版本 + 提交 + 打 tag + 推 git | 本地 |
| `.env.harbor.example` | Harbor 配置模板（复制成 `.env.harbor` 填地址） | 本地 |
| `.env.harbor` | Harbor 地址与账号（已 gitignore，不入库） | 本地 |
